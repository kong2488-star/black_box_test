# AVI 입력이 탐지를 무너뜨린다 (실측, 재현됨)

2026-09-15. `video/20260620_141927_EVT_1.avi` 누락 조사 중 나온 별건이자, 그 누락의 실제 원인.

원본 AVI 와, 그것을 **무손실 리먹스**한 mp4 를 비교했다. 픽셀 데이터는 동일하다:

```bash
ffmpeg -i video/20260620_141927_EVT_1.avi -map 0:v:0 -c:v copy -an -sn \
       -movflags +faststart 141927_remux.mp4
```

AVI 원본: h264 1920x1080 30fps 601프레임 + PCM 오디오 + 데이터 스트림(주행정보 추정).
리먹스는 비디오 스트림만 그대로 옮긴다. **재인코딩 없음 = 화질 변화 없음.**

## 1. Coarse — 같은 영상인데 AVI 는 0건, mp4 는 1건

`gemini-3.7-flash` · low · 1fps · prompt `1a77e2b1c5f3` · offset 없음

| tag | AVI 후보 | mp4 후보 | mp4 span |
|---|---|---|---|
| `remux_check` | – | 1 | 12.0–18.0s (at 15.0, score 0.90) |
| `rep1` | **0** | **1** | 11.0–16.0s (at 13.0, score 0.90) |
| `rep2` | **0** | **1** | 11.0–16.0s (at 13.0, score 0.85) |
| `rep3` | **0** | **1** | 12.0–17.0s (at 14.5, score 0.85) |

AVI 는 이전 회차까지 합쳐 **7회 전부 0건**(low@1fps, high@2fps, high@5fps, no-schema@high5,
프롬프트 p1/p2). mp4 는 **4회 전부 1건**, span 도 11~18s 안에서 안정적이다.
**노이즈가 아니라 신호다.**

## 2. Fine — offset 을 걸면 AVI 는 영상이 거의 안 간다

`CLAUDE.md` 의 불변식("플래그를 믿지 말고 토큰 수로 확인한다")이 잡아낸 건이다.
high@2fps 의 기준값은 **553 tok/영상초**다.

| 입력 | offset | 구간 | video 토큰 | tok/초 | 판정 |
|---|---|---|---|---|---|
| AVI | 5500–11000ms | 5.5s | **137** | **24.9** | (무효) |
| mp4 리먹스 | 5500–11000ms | 5.5s | 2904 | 528.0 | NOT_OBSERVED |
| mp4 리먹스 | 9000–18000ms | 9.0s | 4752 | 528.0 | NOT_OBSERVED |
| (대조) mp4 chunks, run1 전체 | 다양 | 8~12s | – | **553.0** | – |

AVI + offset 은 기대치의 **1/22** 만 전달된다. 에러도 경고도 없다.
5.5초 구간을 요청했는데 모델은 사실상 정지영상 한두 장을 받는다.

**해상도·fps 자체는 AVI 에서 정상이다.** 같은 AVI 를 offset 없이 high@2fps 로 부르면
552.3 tok/초가 나온다(`diagnosis_high2fps`). 즉 **깨지는 것은 `start_offset`/`end_offset`
하나**다. AVI 컨테이너의 시간 인덱스가 Files API 쪽 seek 과 맞지 않는 것으로 보인다.

## 2-1. 붕괴된 행의 판정은 동전던지기다

같은 AVI 구간(video 토큰 137개로 고정)을 두 번 물렸더니 판정이 갈렸다:

| tag | video tok | 판정 |
|---|---|---|
| `guard_check` | 137 | **OBSERVED** |
| `guard_check2` | 137 | **NOT_OBSERVED** |

입력·프롬프트·조건이 전부 같은데 결론이 반대다. 모델이 사실상 아무것도 못 본 상태라
판정이 난수와 다르지 않다는 뜻이다. **붕괴된 행은 "놓쳤다"는 증거로도,
"잡았다"는 증거로도 쓸 수 없다.** 세지 말고 버려야 한다.

## 2-2. 이제 코드가 막는다 (2026-09-15)

두 탐침에 `check_video_delivery()` 가 들어갔다. video 모달리티 토큰을
`프레임당 기대치 x 프레임수` 와 대조해 각 행에 flag 를 남긴다.

- `VIDEO_TOKENS_LOW` — 기대의 50% 미만. 요청한 구간이 전달되지 않았다.
- `VIDEO_TOKENS_HIGH` — 기대의 200% 초과. 구간 지정이 통째로 무시됐다(원가도 그만큼).
- `NOT_AUDITABLE` — 검산에 필요한 값이 없다. **통과가 아니라 미검사다.**

기준값은 실측이며 medium/ultra_high 는 비워 뒀다 — 없는 값을 지어내면 경보가 거짓말을 한다.
리포트는 jsonl 에서 파생되므로 flag 필드가 생기기 전의 옛 행도 소급 판정한다.
실제로 소급 검산이 세 건을 잡아냈다:

| 후보 | tag | flag | 비율 |
|---|---|---|---|
| part_01.mp4#0 | `smoke` | VIDEO_TOKENS_HIGH | 2080% |
| 20260620_141927_EVT_1.avi#M0 | `bypass_141927` | VIDEO_TOKENS_LOW | 5% |
| 20260620_141927_EVT_1.avi#M1 | `bypass_141927` | VIDEO_TOKENS_LOW | 5% |

`smoke` 는 google-genai 2.12.1 시절 회차다. **그때 이 검산이 있었으면 그 자리에서 잡혔다.**

## 3. 그래서 어떻게 해야 하는가

- **블랙박스 AVI 를 그대로 파이프라인에 넣지 않는다.** 업로드 전에 mp4 로 리먹스한다.
  재인코딩이 아니라 `-c:v copy` 리먹스이므로 비용도 화질 손실도 없다.
- ~~`tokens_per_sec_of_video` 를 video 토큰 기준으로 본다.~~ **고쳤다.**
  두 스크립트 모두 video 모달리티 토큰으로 계산하고, 리포트는 옛 행까지 다시 계산한다.
  입력토큰 기준 값은 "검산에 쓰지 말 것"이라고 이름표를 붙여 따로 남겼다.
- 제품 레포로 옮길 때: 업로드 경로에 컨테이너 정규화 단계가 필요하다.
  `contract-*` 에 없는 단계이므로 search Owner 가 올릴 사항이다.

## 4. 남은 쟁점 — 실선인가 점선인가

mp4 로 파이프라인이 기계적으로는 정상 작동한다. 그런데 판정이 갈린다:

- Coarse(mp4): "전방의 짙은 색 SUV가 1차로에서 **백색 점선**을 넘어 2차로로 차로를 변경함"
- Fine(mp4, 9–18s 구간): `WHITE_SOLID_LINE` **ABSENT** / `WHITE_DASHED_LINE` **PRESENT**,
  `VEHICLE_CROSSED_DASHED_LINE` at 13.5s → **NOT_OBSERVED**
- 사람(Owner): 이 클립에 **실선 차로변경 위반이 있다**

세 판단이 t≈13.5s 의 선 종류에서 충돌한다. 가능성은 둘이다:

1. 모델 둘 다 t≈13.5s 의 선을 오판했다 (실선을 점선으로).
2. t≈13.5s 의 차로변경은 실제로 점선(합법)이고, **위반은 다른 시각의 다른 기동**이다.
   교량부 t≈5.5~12s 구간의 차로 경계는 실선으로 보이며, 그 구간에서도
   같은 SUV 가 횡방향으로 이동한다. 그렇다면 Coarse·Fine 은 **위반 기동은 통째로 놓치고
   뒤따르는 합법 기동만 잡은 것**이 된다 — 훨씬 나쁜 실패 양상이다.

**사람이 확정해 줘야 갈린다.** 확정 전까지 이 클립을 정답지로 쓰지 않는다.
